# How new and customised components reach the library

1. **Build it locally.** `node ui/twinx/cli/bin/twinx-ui.mjs new <name>` (new component) or
   `… new <name> --extends <component>` (a variant of a library component). Files land in
   `ui/local/components/<name>/`: `component.json`, `<name>.css`, `<name>.html` (examples), optional `<name>.js`.
2. **Use it.** `ui/local/local.css` (and `local.js`) are regenerated by `twinx-ui build`; the Claude Code hooks
   run it for you after each edit. The component shows in `ui/catalog.html` with a "Local" badge.
3. **Contribute it.** When it is finished (no TODOs, lint clean):
   `node ui/twinx/cli/bin/twinx-ui.mjs contribute <name>`. This clones the TwinX library repo, adds the
   component (or merges the variant into the component it extends), rebuilds the library catalog, and opens a
   pull request with the GitHub CLI (`gh`). Without push access it uses a fork.
4. **Review.** The library owner (Muthu) reviews the pull request in all five themes and merges it. Merging is the
   approval: the component becomes part of `twinx.css` in the next release tag.
5. **Update.** `node ui/twinx/cli/bin/twinx-ui.mjs update v1.x.y` (or `npx github:Muthukumar18121989/tcs-twinx-3.0-ui#v1.x.y sync`)
   brings the new version in. Delete your local copy once the library has it (sync tells you).

Naming: `tx-<component>` for a component, `tx-<component>--<variant>` for a variant, `tx-<component>__<part>` for
a part. Kebab case. One folder per component.
